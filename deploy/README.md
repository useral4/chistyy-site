# VPS: перенос, защита и восстановление

Конфигурация подготовлена, но ещё не развёрнута. VPS не выбран, Docker и реальная PostgreSQL-интеграция на этой рабочей машине не проверены. Не переключать DNS до выполнения всех проверок ниже. Обычная публикация на Render оставляет файловое хранилище и прежний встроенный Chromium; его Linux-конфигурация не равнозначна sandbox нового VPS-обработчика.

## Сервер

Начальная конфигурация: 2 vCPU, 4 ГБ RAM, от 40 ГБ SSD, Debian 12, размещение в РФ. Нужны аварийная консоль, SSH по ключу, 2FA панели, обновления, защита HTTP/HTTPS L7 и отдельное резервное хранилище. У провайдера нужно уточнить цену L7: защита сетевого уровня L3/L4 её не заменяет. Ни дорогой сервер, ни WAF не исключают взлом или отказ.

Код ограничивает полный аудит одной одновременно выполняющейся задачей, до 20 ожидают не больше 120 секунд. После получения места время ограничено 90 секундами, объём основного процесса — 16 МБ, каждый ресурс — 2 МБ, загрузка ресурсов идёт группами по четыре. Browser worker имеет свои ограничения и контейнерный лимит 1536 МБ. Повторить отклонённую проверку можно позже; очередь не сохраняется при перезапуске. Это не бесконечная очередь и не обещание времени 60 секунд под нагрузкой.

Локальное измерение одного аудита: около 10 секунд и 574 МБ суммарного рабочего набора Node/Edge на Windows. Это не прогноз для всех сайтов и не результат нагрузочного теста VPS. При устойчивой очереди сначала измерить длительность, CPU, память и ошибки на VPS. Затем увеличить мощность или добавить отдельные обработчики и общую очередь. Не поднимать параллелизм без измерений. PostgreSQL готовит хранилище к нескольким процессам, но очередь и rate limit пока локальны.

## Подготовка

1. Создать отдельного администратора с SSH-ключом, проверить второй вход и аварийную консоль. Только после этого ограничивать SSH и отключать пароль/root-login. Не выполнять удалённо универсальный firewall-скрипт без проверки доступного порта SSH.
2. Установить Docker Engine и Compose из [официальной инструкции Debian](https://docs.docker.com/engine/install/debian/), Restic из проверенного репозитория ОС. Членство в группе Docker даёт полномочия root; не выдавать его посторонним.
3. Разместить репозиторий в `/opt/kinavapro`. Заполнить `/opt/kinavapro/.env` по корневому шаблону: настройки почты, тестовой оплаты, `OPS_EMAIL`. Не активировать реальные платежи. Файл не попадает в контейнерный образ.
4. Заполнить `deploy/.env` по `deploy/.env.example`: домен, ACME email, четыре разных случайных секрета `POSTGRES_PASSWORD`, `APP_DATABASE_PASSWORD`, `BROWSER_WORKER_KEY`, `METRICS_TOKEN`. Для каждого подходит вывод `openssl rand -hex 32`; пароль БД должен быть URL-safe. `chmod 600 .env deploy/.env`. Не помещать секреты в чат или Git. Не печатать полный `docker compose config` с секретами в общие журналы.
5. Проверить отсутствие конфликта подсети `172.30.0.0/24`. Если она занята, согласованно поменять подсеть, адреса app/worker, URL обработчика и правила firewall. Корневой `.env` не должен переопределять `PORT`, `BROWSER_EXECUTABLE_PATH` или включать `BROWSER_AUDIT=off`.

Compose публикует только 80/443. БД, метрики и worker не имеют публичных портов; Caddy дополнительно закрывает `/metrics` и `/readyz`. Прокси перезаписывает клиентский IP для rate limit. У Docker свои цепочки firewall: UFW сам по себе не гарантирует закрытие опубликованных портов. Внешний firewall провайдера должен разрешать только нужные публичные порты и выбранный SSH-доступ.

При первом запуске пустой БД `init-database.sh` создаёт отдельную роль приложения без прав SUPERUSER/CREATEDB/CREATEROLE. Администратор `postgres` имеет другой пароль и не передаётся app. Скрипт выполняется только для нового тома: смена `.env` не меняет пароль существующей роли. Ротацию выполнять отдельно через администратора, не удаляя том.

Worker запускается не от root, без capabilities, с `chromiumSandbox: true`, seccomp, read-only filesystem и лимитами CPU/RAM/PID. Он получает только URL и отдельный ключ, не получает почту, оплату, отчёты, пользовательские cookie или тома БД. Это дополнительная изоляция, не виртуальная машина и не абсолютная защита от уязвимости ядра. Правила `worker-firewall.sh` блокируют обращения к частным сетям и самому хосту, оставляя публичный HTTP/HTTPS и DNS.

`seccomp_profile.json` взят из [Microsoft Playwright v1.63.0](https://github.com/microsoft/playwright/blob/v1.63.0/utils/docker/seccomp_profile.json), SHA256 `cc3e61cabda6bbc1e53e54d27ba4d55a9d3be829b6dd1a596f4a7b31b1cc7849`. Sandbox-подход: [документация Playwright](https://playwright.dev/docs/docker). Не добавлять `--no-sandbox` или `SYS_ADMIN`, если Chromium не запустился; исправить причину и проверить ядро/user namespaces.

## Миграция без потери доступа

Сначала сделать защищённую копию всего старого `REPORTS_DIR`, включая `passes/`, и `LEADS_DIR`. Убедиться, что скопированы существующие оплаченные отчёты, а не пустой каталог новой установки. Остановить новые проверки, оплаты и запись на старом сервере перед последним экспортом. Не удалять старые данные и не менять одновременно ключи ссылок.

Из `/opt/kinavapro/deploy` после настройки секретов:

```sh
docker compose config --quiet
docker compose build app worker
docker compose up -d database
docker compose run --rm --no-deps -T --volume /secure-export/reports:/migration:ro app node scripts/migrate-storage.js /migration
```

`/secure-export/reports` — абсолютный каталог проверенного экспорта на VPS, не на рабочем ПК. Миграция проверяет формат, вставляет отсутствующие записи, сравнивает уже существующие и останавливается при конфликте. Её можно повторить после исправления причины; файлы не удаляются. Пустую БД нельзя включать на действующем сайте без переноса.

Заявки остаются в отдельном томе `leads`: перенести их с сохранением владельца `node` (UID/GID 1000) и ограничений доступа. Для импорта можно воспользоваться временным app-контейнером с read-only экспортом, не монтируя весь домашний каталог администратора. БД хранит отчёты, платежные состояния и пакеты; заявки и состояние мониторинга находятся в томах. Не применять `docker compose down --volumes`.

## Предпусковая проверка

Установить firewall до запуска worker и повторно проверить после перезапуска Docker. Нельзя считать правила установленными по одному наличию файла в Git:

```sh
sudo install -m 644 kinavapro-firewall.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now kinavapro-firewall.service
docker compose up -d worker app web
docker compose ps
docker compose logs --tail 100 worker app
```

Обязательно проверить:

- Полный аудит публичного тестового сайта: настоящий `browserChecked=true`, отказ при недоступном worker, без перехода на небезопасный браузер. `/healthz` worker проверяет только HTTP-сервис, не запуск Chromium.
- SSRF: частные IP, localhost, metadata, редирект на частный адрес не доступны; TCP из worker к хосту/БД блокируется, DNS и публичный HTTPS работают.
- PostgreSQL: после пересоздания app доступны старые ссылки и пакеты; конкурентные проверки не превышают квоту, ошибка записи откатывает списание. Автотесты транзакций используют mock; здесь требуется реальная БД.
- Очередь: две одновременные проверки показывают реальное ожидание, отмена удаляет ожидающую задачу, переполнение даёт понятную ошибку, 100% наступает только после сохранения.
- Внешняя сеть: 4173, 4180 и 5432 закрыты, `/metrics` и `/readyz` извне возвращают 404. Отчёты и личные ссылки не кешируются CDN; кешировать только публичную статику.
- TLS и CSP: форма, отчёт, тестовая оплата и Метрика после согласия работают; certificate выдаётся после правильной настройки DNS. До переключения домена можно использовать временный тестовый домен.
- 30–60 минут контролируемой нагрузки с известными публичными сайтами: память не достигает лимита, нет OOM/restart, очередь восстанавливается. Не запускать нагрузочный тест на чужом сайте или текущем продакшене без согласования.

Только после реального восстановления резервной копии и этих проверок переключать DNS. Старый сервер оставлять выключенным для записи, но сохранять для отката. После переключения проверить старые ссылки ещё раз. Обратное переключение после новых оплат/аудитов требует переноса новых записей; старая копия уже не актуальна.

## Резервные копии и уведомления

Резервное хранилище должно быть вне этого VPS, с отдельными ограниченными учётными данными и защитой от удаления, если провайдер поддерживает Object Lock/append-only. Поддерживаемые Restic адреса перечислены в `backup.sh`. Выбрать место хранения с учётом фактических данных. Шифрование не заменяет выбор допустимого размещения. Пароль Restic хранить также в отдельном защищённом хранилище: без него восстановление невозможно.

Создать `/etc/kinavapro-backup.env` по `backup.env.example` и отдельный `RESTIC_PASSWORD_FILE`, оба root-only 600. Создать каталоги `/var/lib/kinavapro-backup` и `/var/cache/kinavapro-restic` с правами 700. Инициализировать новый репозиторий Restic с этими переменными вручную, не перезаписывая существующий. Проверить `restic snapshots` и `restic check`.

Установить backup/monitor service и timer из этой папки в `/etc/systemd/system`, выполнить daemon-reload. Сначала вручную запустить `kinavapro-backup.service`, проверить успешный внешний снимок и выполнить пробное восстановление. Только затем включить `kinavapro-backup.timer` (каждые 15 минут) и `kinavapro-monitor.timer` (каждую минуту). Секреты сервисов не должны попадать в journal или shell history.

Бэкап включает pg_dump и архив заявок. Это согласованный снимок БД; архив файлов создаётся отдельно, не как атомарный снимок всех служб. Копия конфигурации/секретов и DNS/доступы хранятся отдельно защищённо. Автоматическое удаление/prune не включено. Цели после успешной настройки: до 15 минут потери данных между успешными копиями, время восстановления измерить на практике; без теста RTO не обещается.

Монитор запускается отдельным краткоживущим контейнером, поэтому может заметить падение app. Он проверяет БД/приложение, очередь, память Node и давность успешного бэкапа. Нужны рабочие SMTP и `OPS_EMAIL`: без них уведомления не доставляются. Проверить тестовое предупреждение и восстановление. Он не следит за своим VPS извне и не измеряет RAM браузера/всего хоста: добавить внешний uptime-monitor с другого сервера/провайдера и уведомления панели о диске, CPU, RAM, OOM. Когда весь VPS выключен, внутренний монитор не работает.

Ежемесячно восстанавливать снимок в изолированную тестовую БД и каталог заявок, проверять старый оплаченный отчёт и лимит пакета. Никогда не направлять тест восстановления в действующую БД. После восстановления не включать почту/уведомления/платежи до проверки состояния. Обновления контейнеров и Chromium выполнять с бэкапом, тестами и планом отката, без автоматического скачивания нового образа в продакшен.

## При инциденте

При перегрузке проверить очередь, метрики, CPU/RAM/диск и журналы рестартов. Не снимать ограничения, чтобы убрать очередь: это может уронить весь сервер. Если нагрузка злонамеренная, ограничить её на L7 у провайдера; rate limit Node не заменяет DDoS-защиту канала.

При подозрении на взлом ограничить доступ/изолировать сервер, сохранить журналы и снимок диска для расследования, отозвать затронутые ключи с чистого устройства. Не считать перезапуск устранением взлома. Развернуть чистый сервер из проверенного кода, обновить уязвимые компоненты, восстановить проверенную копию, сменить секреты, сверить состояния оплат и доступов. Если затронуты персональные данные, оператор отдельно оценивает обязательные уведомления и действия. Не обещать пользователям отсутствие утечки без расследования.
